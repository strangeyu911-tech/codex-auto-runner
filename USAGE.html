1. 这是什么

长任务跑到一半，5h 额度耗尽。上下文还在、目标还在、任务没结束，但下一次额度恢复时人不一定守在电脑前。 Codex Auto Runner 就是为这一刻准备的：它在本机盯着真实额度，等窗口恢复、二次确认额度确实可用， 然后恢复同一个 Codex 线程，把任务接着往下推。

它要解决的不是「如何绕过限制」，而是「如何不浪费已经恢复的额度」。 它是一个非官方本地工具，不突破、不规避、不修改任何额度规则。

它是本机工具：daemon 只监听 127.0.0.1，HTTP API 的 /api/* 需要本地随机 token 鉴权（静态前端页面本身免 token，否则浏览器打不开）。 它不自动 push、不自动部署、不替你接受高风险审批。

2. 快速开始

本机没有安装 pnpm（pnpm 不在 PATH 上）。 仓库 README 里写的 pnpm xxx 命令在本机跑不通，请用下面这些 node 直调命令。 pnpm 只是包管理/任务编排的便利层，核心逻辑全部由 node 驱动，跳过它不影响功能。

2.1 启动 daemon（守护进程）

双击仓库根目录的 start-daemon.cmd，或手动执行：

:: 在仓库根目录执行
node node_modules\tsx\dist\cli.mjs apps\daemon\src\index.ts

看到 http api listening 与 http api ready 即为启动成功。daemon 会：

  • 连接 Codex app-server，读取真实额度桶（5h + 周）
  • 按真实 reset 时间安排唤醒，并在唤醒点做抖动后的二次验证
  • 调度任务队列、提供本地 HTTP API、把状态写入 SQLite

2.2 启动前端（另开一个窗口）

cd apps\web
node node_modules\vite\bin\vite.js

然后浏览器打开 http://127.0.0.1:5173/。

顺序很重要：先启动 daemon，再启动前端。 前端在启动时读取 daemon 写下的 api.json 来拿端口和 token； 如果先起前端，它拿不到 token，界面会请求失败（401）。

想知道当前 daemon 用的是哪个端口：

type "%LOCALAPPDATA%\CodexAutoRunner\data\api.json"

2.4 生产模式：只跑 daemon 一个进程

不想常驻一个 Vite 进程的话，可以让 daemon 直接伺服前端构建产物——一个端口、一个进程。 前置条件是 apps/web/dist 已经构建过。 

:: 1) 构建前端（仅代码变更后需要重跑）
cd apps\web
node node_modules\vite\bin\vite.js build

:: 2) 回到仓库根目录，确认 daemon 在跑，取端口
type "%LOCALAPPDATA%\CodexAutoRunner\data\api.json"

:: 3) 取 token
type "%LOCALAPPDATA%\CodexAutoRunner\data\car-api.token"

然后打开 http://127.0.0.1:<端口>/。页面本身能正常加载，但首次调用 API 会弹出粘贴框， 把 car-api.token 的内容粘进去即可，之后由浏览器记住。 也可以一步到位地用 http://127.0.0.1:<端口>/#token=<token>，页面会读取 hash 里的 token 并自动清掉 hash。

为什么首页能直接打开，但还是要手动带一次 token？ 静态资源免鉴权（浏览器加载页面时无法附加自定义请求头），但 /api/* 仍需 token。 页面本身不会替你注入 token——否则任何本机进程只要请求一次首页就能拿到凭证，token 就失去意义了。 把 token 放在 URL 的 # 片段里，片段不会发送给服务器，只留在你的浏览器中。

build 与 daemon 的先后顺序无所谓。 前端目录是惰性解析的：daemon 启动之后才 build 出来的 dist，下一次请求就会被接管， 不需要重启 daemon。

3. 核心工作流

  1. 在 Codex 里把任务跑起来 在一个 Codex 会话里正常干活，跑到 5h 额度耗尽为止。不需要提前做任何特殊设置。
  2. 在 Web UI 里选中那个会话 打开「新建任务」，选择要接管的 Codex 会话。 列表里会标注每个会话是否「当前加载」、是否设置过目标，以及是否上次因 5h 限额中断。
  3. 创建续跑任务 切换到「自动版」，确认目标与「继续指令」后创建任务。 任务会以 resume_thread 模式绑定这个线程——不新建空会话，沿用原上下文。
  4. 放手，让它自己接棒 额度耗尽 → 任务进入 WAITING_QUOTA → 到点后二次确认额度 → 恢复同一线程 → 继续推进。 循环直到任务完成、需要你判断，或周额度被充分消耗。

4. 无 goal 续跑（新增）

重要变化 早期版本的自动版只支持已开启「目标模式」的会话，没有设置 goal 的会话会被前端拦住。 现在这条限制已经解除：没有设置 goal 的线程同样可以被接管并跨额度窗口续跑。

这依赖三件事：

能力说明
识别「谁被限额打断」 命中限额时把线程 id + 时间落库。关键点：不依赖 goal——因为无 goal 线程读目标是 null，据此判断必然漏判。
优先续跑最新的那条 同时有多条被 5h 限制中断的线程时，优先续跑最新被打断的那条；会话列表与调度认领都按这个顺序。
重启后保住语义 daemon 重启时，被限额打断的任务会回到 WAITING_QUOTA（等额度自动接着跑），而不是一律降级成 WAITING_USER 要求你手动确认。

你显式设置的优先级依然优先。 「被打断优先」只在优先级相同的前提下生效，不会掀翻你自己设定的高优先级任务。

界面上的表现

  • 会话列表里被限额打断过的线程会带一个 「上次因 5h 限额中断」 角标，并显示中断时间。
  • 默认选中项会优先落在最近被打断的那个线程，不用你自己往下翻找。
  • 无 goal 会话的说明文字为「未开启目标模式（可直接按会话上下文续跑）」。

5. 如何确认它真在跑

不要用 Codex 桌面版 GUI 判断任务有没有在跑。 daemon 用的是从 MSIX 单独复制的 codex.exe，和桌面 GUI 是两个进程， 只共享 ~/.codex 数据目录。GUI 不会实时刷新别的进程写入的回合， 所以你很可能在界面里「看不到任何动静」，但任务其实跑得好好的。

按下面三条链路核实（从轻到重）：

① 看任务状态

Web UI 的任务列表，或命令行：

node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts status

② 看事件流

events.jsonl 会追加关键事件，这是最直接的「它动过」的证据：

type "%LOCALAPPDATA%\CodexAutoRunner\data\events.jsonl"

关注这几类：quota/interrupted（被限额打断）、quota/recovered（额度恢复）、 thread.resumed（线程已恢复）、turn/started、turn/completed。

③ 看 Codex 会话文件是否被写入

这是最终事实来源。检查会话 rollout 文件的修改时间：

Codex 的数据目录默认为 %USERPROFILE%\.codex（即 CODEX_HOME）， 会话记录放在它下面的 sessions 子目录里：

:: 列出最近被写入的会话文件（按时间倒序）
dir /s /o-d "<CODEX_HOME>\sessions\*.jsonl"

如果 rollout-*.jsonl 的修改时间就在刚才，说明 Codex 确实在产出内容， 只是 GUI 还没刷出来。切换会话或重启桌面版即可看到新回复。

6. 任务状态含义

状态含义
READY已就绪，等待调度器认领
RUNNING正在执行一个回合（turn）
WAITING_QUOTA被 5h/周额度打断，等额度恢复后自动继续
WAITING_AUTH需要登录，暂停自动推进
WAITING_USER需要你判断（验证失败、无进展、非额度异常中断等）
VERIFYING回合结束，正在跑验证命令
NEEDS_CONTINUE任务未完成但仍有进展，稍后自动继续
PAUSED已暂停，不再被自动调度
COMPLETED完成（验收标准全部通过）
FAILED_RETRYABLE失败但可重试，稍后重投
RECOVERINGdaemon 重启时发现的「异常运行中」任务，等待归类

7. 命令速查

本机无 pnpm，统一用 node + tsx 直调 CLI：

:: 简写：在仓库根目录把下面这行设为 CAR
:: node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts

node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts status          # 额度 + 任务概览
node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts quota           # 仅额度详情
node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts task list       # 任务列表
node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts task show <id>   # 任务详情
node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts task run-now <id> # 立即运行
node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts task pause <id>  # 暂停
node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts task resume <id> # 恢复
node node_modules\tsx\dist\cli.mjs apps\cli\src\index.ts task cancel <id> # 取消

pause / resume / run-now 直接写数据库；daemon 的调度器在下一个 tick 读取。 daemon 没在跑时状态照样写入，启动后会被处理。

9. 数据与文件位置

%LOCALAPPDATA%\CodexAutoRunner\ ├── data\ │ ├── runner.db # SQLite：任务、事件、锁、额度快照 │ ├── api.json # daemon 端口 + token 文件位置 │ ├── car-api.token # 本地 API token │ ├── status.json # 最近一次额度快照 │ ├── events.jsonl # 关键事件流（额度恢复等） │ ├── settings.json # 自动运行开关 │ ├── daemon.lock # 单实例锁 │ └── tasks\ # 每个任务的 checkpoint └── codex-portable\ └── codex.exe # 从 MSIX 复制的独立副本

Codex 侧的数据（会话历史）仍在原本的位置：%USERPROFILE%\.codex\。 daemon 与桌面版共享它，所以续跑的产出对 GUI 是可见的——只是需要手动刷新。

10. 常见问题

打开前端一片空白 / 提示未授权

先分清是「页面根本没打开」还是「页面打开了但数据是空的」：

  • 连页面都打不开：daemon 没在跑，或者访问的端口不对。 确认有 http api ready 日志，并用 api.json 里的端口访问。
  • 页面出来了但提示未授权 / 数据空：缺 token。把 %LOCALAPPDATA%\CodexAutoRunner\data\car-api.token 的内容填进弹出的粘贴框， 或在 URL 上加 #token=<token>。
  • Vite 开发模式（5173）报错：多半是启动顺序反了——必须先起 daemon 再起前端， 前端启动时要从 api.json 读端口和 token。

任务一直不动，也不报错

多半是额度状态是 unknown。这通常意味着读取额度桶的网络请求失败了， 调度器在额度未知时会保守地不启动任务（这是设计行为，不是 bug）。 检查 status.json 里的 status 字段，网络恢复后会自动继续。

提示 dirty worktree，任务不跑

工作区有未提交改动。确认不需要提交后，设置 CAR_ALLOW_DIRTY=1 再启动 daemon （start-daemon.cmd 里已经默认设置）。它不会 stash 或 reset 你的任何改动。

Codex 桌面版里看不到续跑的内容

正常现象，见第 5 节。daemon 与 GUI 是两个进程，GUI 不实时刷新别的进程写入的回合。 以 events.jsonl 和 sessions 目录下 rollout-*.jsonl 的修改时间为准。

同时有好几个会话都被限额打断，会跑哪个？

优先跑最新被打断的那条。其余保持等待，当前任务跑完后再按同样顺序认领。 如果你想让某个任务先跑，把它的优先级调高即可——显式优先级高于「被打断」加成。

额度显示 100% 了，是不是完全不能跑了？

不一定。5h 桶打满时 Codex 可能降级回退到备用模型继续工作。 另外若开启了「周额度重置次数续跑」，周额度耗尽时也可消耗重置次数继续。

11. 安全边界

  • daemon 只监听 127.0.0.1，不对外暴露。
  • 本地 HTTP API 的 /api/* 需要随机 token 鉴权；token 只存在本机数据目录。
  • 静态前端资源（SPA 外壳）不做鉴权，因为浏览器加载页面时无法附加自定义请求头。 它只包含构建产物、不含任何机密；数据与所有写操作仍然走需要 token 的 /api/*。 静态目录另有越界校验，/../../ 之类路径无法读到 dist 之外的文件。
  • 不自动 push、不自动部署、不替你接受高风险审批。
  • 不修改 Git 历史（不发 reset --hard / push --force / clean -fd）。
  • Codex 网络访问默认关闭，需要显式开启。
  • 日志会脱敏 token、authorization、secret、账号标识等字段；本机路径前缀也会被脱敏。
  • 额度未知、需要登录、项目被锁定、验证失败或需要人工判断时，调度器会停止自动推进。
  • .env、日志、数据库、构建产物、探针转储等均被 .gitignore 排除，不会进仓库。

提交前跑一次隐私检查：

node node_modules\tsx\dist\cli.mjs scripts\privacy-check.ts

它会扫描仓库文件，发现真实用户路径、Codex 私有会话路径、常见 API Key、GitHub token 等时直接失败。
